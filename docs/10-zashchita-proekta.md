## 10.3. Чистая архитектура: как доказать за 30 секунд

### Сначала суть в двух предложениях

Чистая архитектура — это **правило направления зависимостей**. Внутренние
слои (правила, данные) не должны ничего знать о внешних (экраны, база,
сеть). Знание идёт только внутрь: экран знает про правила, правила про
экран — нет.

Зачем: поменять экран, базу или способ доставки данных можно, не трогая
то, ради чего приложение существует.

### Обычная проблема

Обычно это соблюдают «по договорённости»: папки названы правильно, и все
обещают не нарушать. Через полгода кто-то торопится — и импортирует
Flutter в файл с правилами. Никто не заметил, архитектура поехала.

### Как сделано здесь

Проект разбит на **три отдельных пакета**, и у каждого свой список
зависимостей:

```
fastwork/                 ← экраны. Зависит от Flutter
├── packages/core/        ← правила и данные. Зависит ТОЛЬКО от drift
└── packages/server/      ← сервер. Зависит от core, но не от Flutter
```

Открой `packages/core/pubspec.yaml` — там всего одна зависимость:

```yaml
dependencies:
  drift: ^2.35.0
```

**Flutter в этом списке нет.** Значит, написать в любом файле `core`
строку `import 'package:flutter/material.dart'` физически невозможно:
такого пакета для него не существует.

### Живой фокус (делай прямо при нём)

Открой `packages/core/lib/shift.dart`, впиши первой строкой:

```dart
import 'package:flutter/material.dart';
```

и выполни в терминале:

```bash
cd packages/core
dart analyze
```

Ответ:

```
error - lib/shift.dart:1:8 - Target of URI doesn't exist:
'package:flutter/material.dart'
```

Убери строку — снова чисто.

Скажи так:

> «Вот в чём разница. Обычно правило архитектуры — это договорённость,
> и её нарушают по невнимательности. Здесь нарушить нельзя: проект
> просто не соберётся. Правило перестало быть словами и стало
> проверкой.»

### Второе доказательство: один интерфейс, пять реализаций

`packages/core/lib/data/shift_repository.dart` — описание того, **что**
умеет хранилище смен, без единого слова о том, **как**:

```dart
abstract class ShiftRepository {
  Future<List<Shift>> shiftsOn(DateTime date, {ShiftFilter filter});
  Future<BookingResult> apply(int shiftId);
  ...
}
```

Выполняют это описание пять разных классов:

| Класс | Где данные | Зачем нужен |
| --- | --- | --- |
| `DbShiftRepository` | SQLite / PostgreSQL | боевой, на сервере и на телефоне |
| `ApiShiftRepository` | на сервере, по сети | в приложении, когда есть сервер |
| `FakeShiftRepository` | в памяти | тесты: мгновенные, без базы |
| `BrokenShiftRepository` | падает нарочно | проверить, что экран переживёт сбой |
| `SlowShiftRepository` | отвечает медленно | проверить, что видно загрузку |

**Экраны не знают, какой из них работает.** Они видят только интерфейс.
Поэтому одно и то же приложение работает и на локальной базе, и через
сервер — файл `lib/main.dart` просто подставляет нужную реализацию:

```dart
const apiUrl = String.fromEnvironment('API_URL');
final repos = apiUrl.isEmpty ? _localRepositories() : _serverRepositories(apiUrl);
```

Скажи:

> «Вот зачем нужен слой репозитория. Когда я переводил приложение
> с локальной базы на сервер, я не тронул ни одного экрана — написал
> пятую реализацию того же интерфейса.»

### Третье доказательство: сервер использует тот же код

`packages/server` подключает `packages/core` и получает те же правила:
проверку мест, срок отмены, порог рейтинга. Правило живёт в одном месте
и работает одинаково на телефоне и на сервере.

## 10.4. Почему выбрано то, что выбрано

Он почти наверняка спросит «почему именно это». Коротко и по делу:

### Flutter + Dart

Один код — телефон и сайт. Для проекта, который нужно показать и на
Android, и в браузере, это экономит ровно половину работы. Плюс Dart
компилируется и в машинный код (для сервера), и в JavaScript (для
браузера) — поэтому сервер написан на том же языке и делит код с
приложением.

### PostgreSQL, а не SQLite

Начинали на SQLite: он лежит файлом рядом с программой, ничего
настраивать не надо, для телефона это правильный выбор.

Но на сервере файл не годится. Хостинг перезапускает программу в новом
контейнере — и файл вместе с данными исчезает. Плюс к файлу не может
одновременно писать несколько процессов.

PostgreSQL — отдельная программа, живущая своей жизнью: данные переживают
перезапуск, несколько соединений одновременно, транзакции.

Важная деталь: **код при этом остался один**. Используется библиотека
drift, а какая база — решает переменная окружения `DATABASE_URL`:

```dart
// packages/server/lib/open_database.dart
QueryExecutor openServerDatabase() {
  final url = Platform.environment['DATABASE_URL'];
  if (url == null || url.isEmpty) return NativeDatabase(File(dbPath));
  return PgDatabase(endpoint: _endpointFrom(url), settings: _settings(url));
}
```

Если спросит про подводные камни — расскажи честно, это сильный ответ:

> «Диалекты SQL разные, и переход выявил четыре несовместимости.
> В SQLite `?` для подстановки значений, в PostgreSQL `$1`. `AVG`
> PostgreSQL возвращает точным типом, и драйвер отдаёт его строкой —
> приходится приводить через `CAST(... AS DOUBLE PRECISION)`. `PRAGMA`
> PostgreSQL не знает вовсе. И булево значение он не считает за число.
> Всё это нашлось только запуском — чтением кода такое не ловится.»

### drift, а не голый SQL

drift — это слой поверх SQL, который проверяет запросы **на этапе
компиляции**: опечатку в имени колонки видно сразу, а не в момент, когда
пользователь нажал кнопку. Плюс он умеет миграции схемы.

Но от SQL он не прячет: сложные запросы написаны настоящим SQL руками —
там, где так понятнее.

### shelf для сервера

Маленькая стандартная библиотека Dart для HTTP. Не фреймворк: нет
магии, весь путь запроса виден глазами.

### Render + Docker

Сервер живёт на Render — бесплатный хостинг. Описан `Dockerfile`:
это инструкция «как собрать и запустить», которую понимает почти любой
хостинг. Сборка в два этапа: в первом полный Dart собирает программу,
во втором остаётся только готовый исполняемый файл. Итоговый образ
меньше, и в нём нечего ломать.

### GitHub Actions

Сборка и выкладывание автоматические. Пушишь в `main` — GitHub прогоняет
тесты, и **только если они прошли**, собирает и публикует сайт и APK.
Непроверенное до пользователя не доезжает.

## 10.5. Как оно работает: путь одного нажатия

Хороший ответ на «покажи, как устроено». Человек нажал «Записаться»:

```
1. Экран            lib/shift_detail_page.dart
                    вызывает repository.apply(shiftId)
                    ↓  экран НЕ знает, куда пойдёт вызов
2. Реализация       lib/data/api_shift_repository.dart
                    POST /api/shifts/12/apply
                    ↓
3. Сервер           packages/server/lib/api.dart
                    проверяет токен, находит пользователя
                    ↓
4. Правила          packages/core/.../shift_repository.dart
                    в транзакции: есть ли места? уже записан?
                    хватает ли рейтинга? не отменена ли смена?
                    ↓
5. База             PostgreSQL: INSERT в application_rows
                    ↓
6. Событие          заказчику пишется уведомление — здесь же,
                    рядом с действием, а не на экране
                    ↓
7. Обратно          BookingResult.ok → экран показывает результат
```

Обрати внимание на шаг 4: **проверки на сервере, а не на экране.**
Скажи об этом сам, не дожидаясь вопроса:

> «Кнопку можно спрятать, но запрос можно отправить и без приложения —
> обычным curl. Поэтому всё, что защищает данные, проверяется там, где
> данные меняются.»

## 10.6. Решения, которые стоит рассказать самому

Это то, что отличает «сделал по туториалу» от «думал головой».

### Не хранить то, что можно вычислить

В базе **нет** колонки «сколько человек набрано». Это число считается
запросом по откликам:

```sql
(SELECT COUNT(*) FROM application_rows a
  WHERE a.shift_id = s.id AND a.status IN ('active','completed')) AS hired
```

Почему: хранимое число живёт своей жизнью. Кто-то отменил запись мимо
одного из мест, где счётчик обновляется, — и он разошёлся с правдой.
Вычисляемое разойтись не может.

Так же считаются: сумма за смену, свободные места, рейтинг, число
отработанных смен, заработок.

### Исключение из этого правила — и почему

Текст уведомления **хранится готовым**, хотя мог бы собираться из смены.
Причина: уведомление — запись о том, что было верно в тот момент. Смену
потом переименуют или отменят, а строчка должна читаться как вчера.

> «Правило "не храни вычисляемое" я нарушил ровно один раз и знаю,
> почему именно там.»

### Состояние — текстом, а не галочкой

У отклика на смену есть состояние: `active`, `cancelled`, `completed`,
`no_show`. Не колонка «подтверждено: да/нет».

Почему: вопрос «вышел ли человек» имеет **три** ответа — вышел, не вышел,
и заказчик ещё не отметил. Галочка третий ответ вместить не может.
Когда позже понадобилось «не вышел», это не потребовало менять базу
вообще.

### Невыход не портит рейтинг

Рейтинг отвечает «как человек работает», надёжность — «приходит ли он
вообще». Это разные вопросы, и в одном числе теряются оба. Поэтому
надёжность — отдельный процент.

Плюс: рейтинг — мнение, его можно передумать, а выход — факт.

### Обновление схемы переживает повторный запуск

Реальная авария на боевом сервере: обновление базы оборвалось
посередине — колонка добавилась, отметка «схема обновлена» не записалась.
Каждый следующий запуск начинал сначала и падал на «колонка уже
существует». База застряла навсегда.

Вывод и исправление: **миграция обязана быть безопасной при повторе.**
Теперь добавление колонки сначала спрашивает у базы, нет ли её уже.

> Это сильная история. Расскажи её — она показывает, что ты чинил
> настоящую аварию, а не только писал новое.

## 10.7. Вопросы, которые он задаст

**«Ты сам это писал?»**
Отвечай честно: активно пользовался ИИ-помощником, но решения принимал
сам и понимаю, почему в коде так, а не иначе. Спрашивай что угодно.
Врать здесь бессмысленно — проверяется одним уточняющим вопросом,
а честный ответ никого не смущает: так сейчас работают все.

**«Где у тебя бизнес-логика?»**
`packages/core` — модели (`shift.dart`, `user.dart`) и хранилища
(`data/`). Ни Flutter, ни HTTP там нет.

**«Как ты тестируешь?»**
128 тестов, три уровня: формулы (без базы), правила на хранилище
в памяти, и отдельный набор против настоящей SQLite — потому что SQL
в памяти не проверяется никак. Плюс экраны целиком через widget-тесты.
Тесты гоняются в CI и блокируют выкладывание.

**«Что с безопасностью?»**
Пароли не хранятся вообще — вход по одноразовому коду на почту.
Сам код тоже не хранится: только его хеш sha256. Код живёт 5 минут,
3 попытки, 5 кодов в час. Токен сессии — случайная строка.
Все проверки прав — на сервере.

**«Что бы ты сделал иначе?»** (готовый честный ответ)
- Приложение подписано отладочным ключом — для настоящей раздачи нужен
  свой ключ в секретах.
- `cleartextTrafficPermitted` в Android включён ради локальной отладки —
  перед релизом убрать.
- Нет постраничной загрузки ленты: пока смен мало, грузим всё.
- Кошелёк показывает заработок, но выплат нет — это сознательно,
  проект учебный.
- Нет push-уведомлений, только внутри приложения.

**«Сколько это кода?»**

| | строк |
| --- | --- |
| Экраны (`lib/`) | 9 040 |
| Суть (`packages/core/`) | 3 984 |
| Сервер (`packages/server/`) | 1 245 |
| Тесты | 2 520 |
| **Всего** | **~14 300** |

12 таблиц в базе, 10 версий схемы, 128 тестов.

Пятнадцать минут, по порядку:

5. **Телефон**: открыть install.html, показать приложение на Android.
6. **Код**: фокус с `dart analyze` (пункт 10.3).
7. **GitHub Actions**: вкладка Actions — показать, что всё собирается
   само и тесты блокируют выкладывание.

## 10.9. Если что-то сломается при показе

- **Сервер отвечает не сразу.** Render на бесплатном тарифе усыпляет
  сервер без запросов. Первый запрос будит его — до минуты. **Открой
  сайт за пять минут до разговора**, чтобы сервер проснулся.
- **Не пришёл код на почту.** Проверь спам. Запасной вариант — заранее
  войти и не выходить.
- **Что-то упало.** Скажи прямо, что случилось, и что посмотришь в
  логах. Спокойная реакция на сбой — тоже часть впечатления.
