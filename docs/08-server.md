# Сервер: что это, как запустить и как выложить в интернет

До сих пор всё жило на одном устройстве. Смена, созданная заказчиком,
никогда не попала бы к исполнителю: у каждого была своя база.

Сервер это исправляет. Теперь база одна, общая, а приложения к ней ходят.

---

## 1. Что изменилось в проекте

Проект стал **тремя пакетами** вместо одного:

```
fastwork/
├── lib/                    ПРИЛОЖЕНИЕ — экраны, Flutter
├── packages/
│   ├── core/               СУТЬ — смены, правила, база. Без Flutter
│   └── server/             СЕРВЕР — HTTP. Без Flutter
├── Dockerfile              как хостингу собрать сервер
└── render.yaml             что хостингу создать: сервис и базу
```

Зачем разделили? Не ради красоты — **иначе сервер не собирался**.

Пока всё лежало в одном пакете, сервер зависел от Flutter. А Flutter —
это библиотека для рисования экранов, весит гигабайты и на сервере ни для
чего не нужна. Хостинг с одним только Dart такую сборку просто не осилил бы.

Теперь зависимости выглядят так:

```
   ПРИЛОЖЕНИЕ  ─────┐
                    ├──►  CORE  (смены, правила, SQL)
   СЕРВЕР      ─────┘
```

`core` не знает ни про приложение, ни про сервер. Оба знают про него.

**Главное следствие:** формулы оплаты, правила записи и весь SQL существуют
в **одном экземпляре**. Сервер считает сумму за смену тем же кодом, что и
приложение, — не похожим, а буквально тем же файлом. Разойтись они не могут.

Это и есть плата за все предыдущие разговоры про слои. Мы держали
`shift.dart` чистым — и он поэтому просто переехал, ничего не сломав.

## 2. Запустить у себя

```powershell
cd packages\server
dart pub get
dart run bin\server.dart
```

Должно появиться:

```
fastwork сервер слушает http://localhost:8080
база: файл SQLite
письма НЕ отправляются — код входа будет напечатан здесь
```

Проверить, что живой — открой в браузере
[http://localhost:8080/api/health](http://localhost:8080/api/health).
Ответ `{"status":"ok"}` значит, что всё в порядке.

**Сервер должен остаться запущенным.** Закроешь окно — он остановится.
Приложение запускай во **втором** окне:

```powershell
flutter run -d chrome --dart-define=API_URL=http://localhost:8080
```

Без `--dart-define` приложение работает по-старому, на своей базе. С ним —
ходит к серверу. Один и тот же код, разница в одной строке при запуске.

### Как убедиться, что это правда сервер

Самая наглядная проверка — та, которая раньше была невозможна:

1. Запусти приложение, зарегистрируйся заказчиком, создай смену
2. Открой **второе окно браузера** и запусти приложение ещё раз
3. Войди исполнителем — и увидишь ту самую смену

Два разных «устройства», одна база. Вот ради чего всё затевалось.

## 3. Выложить в интернет

Ниже — на примере Render. Другие хостинги (Railway, Fly.io) устроены
похоже: подключаешь репозиторий, они читают `Dockerfile` и собирают.

**Условия бесплатных тарифов меняются — перед регистрацией посмотри
актуальные на сайте.**

### Шаги

1. Зайди на [render.com](https://render.com), зарегистрируйся через GitHub
2. **New → Web Service**
3. Выбери свой репозиторий `kiray228/fastwork`
4. Проверь, что выбрана нужная ветка
5. **Runtime: Docker** — остальное Render возьмёт из `Dockerfile`
6. **Create Web Service**

Первая сборка идёт несколько минут. Когда закончится, Render покажет адрес
вида `https://fastwork-server-xxxx.onrender.com`.

Проверь его так же: открой `<адрес>/api/health`, ждём `{"status":"ok"}`.

### Направить приложение на него

```powershell
flutter run -d chrome --dart-define=API_URL=https://fastwork-server-xxxx.onrender.com
```

Всё. Ноутбук больше не нужен — сервер живёт в интернете сам.

### Два подвоха бесплатного тарифа

**Засыпает.** Без обращений сервис останавливается, и первый запрос после
паузы идёт около минуты. Приложение в это время покажет ошибку связи —
это не поломка, просто сервер просыпается.

**Диск временный.** Без постоянного диска файл базы живёт только до
перезапуска. Именно поэтому в `render.yaml` описана отдельная база
PostgreSQL — см. раздел 7. С ней данные не пропадают.

## 4. Как устроен разговор приложения с сервером

### Адреса

Каждый адрес — одно умение. Присмотрись: это те же умения, что в
`ShiftRepository`. Не совпадение — интерфейс хранилища мы писали как
список того, что нужно приложению, и сервер обязан отдавать именно это.

| Адрес | Что делает |
|---|---|
| `POST /api/auth/request-code` | выслать код на почту |
| `POST /api/auth/verify` | проверить код, выдать токен |
| `POST /api/auth/register` | создать аккаунт (после подтверждённой почты) |
| `GET /api/shifts?date=...` | лента на день |
| `GET /api/shifts/<id>` | одна смена |
| `POST /api/shifts/<id>/apply` | записаться |
| `POST /api/shifts/<id>/checkin` | отметиться на месте |
| `POST /api/shifts/<id>/confirm` | заказчик подтверждает выход |
| `GET /api/my-shifts?archived=...` | мои смены |
| `POST /api/shifts` | создать смену |
| `GET /api/health` | жив ли сервер |

`GET` — «дай посмотреть», `POST` — «сделай что-нибудь». Это соглашение, и
его стоит держать: браузеры и прокси считают `GET` безопасным и могут его
повторить или закэшировать.

### Кто спрашивает

При входе сервер выдаёт **токен** — длинную случайную строку. Приложение
прикладывает её к каждому запросу:

```
Authorization: Bearer UHAnSbx9h3HGHvAbOCFsXG4kG9YmydTu
```

Почему не присылать просто номер пользователя? Потому что его легко
подделать: написал чужой — и ты уже кто-то другой. Токен угадать нельзя.

### Почему сервер всё проверяет заново

В коде сервера проверок больше, чем кажется нужным: и что номер свободен,
и что роль подходит, и что оценка от 1 до 5. Всё это уже проверяет
приложение.

Правило простое: **сервер не верит клиенту**. К серверу можно обратиться
в обход приложения — тем же `curl`, одной строкой. Тогда никаких проверок
на той стороне нет вообще. Спрятать кнопку — это удобство, а не защита.

### Чего в нашей авторизации нет

Вход теперь по коду с почты — подробно в разделе 6. Что осталось
упрощённым, там же в конце.

## 5. Что где смотреть, когда сломалось

**Приложение показывает «Нет связи с сервером»** — сервер не запущен,
не тот адрес в `--dart-define`, или (в облаке) сервис спит. Проверь
`/api/health`.

**Сервер ругается при запуске** — скорее всего, порт 8080 уже занят
другой программой. Запусти на другом: `PORT=8090 dart run bin/server.dart`.

**Сервер отвечает, а данных нет** — посмотри в окно сервера. Он пишет
каждый запрос строкой вида `GET [200] /api/shifts`. Код `401` значит
«не узнал тебя», `403` — «это не твоя роль», `404` — «не нашёл».

**В облаке пропали данные после перезапуска** — значит, сервер работает
на файле, а не на PostgreSQL. Проверь, что переменная `DATABASE_URL`
задана: при запуске сервер пишет, какую базу выбрал. См. раздел 7.

## 6. Вход по коду с почты

### Как это выглядит

Три шага вместо одного:

```
  почта  ──►  код из письма  ──►  анкета (только для новых)
```

Если аккаунт с такой почтой уже есть, третий шаг пропускается.

### Где взять код, пока почта не подключена

**В окне сервера.** Он печатает его прямо туда:

```
  ┌────────────────────────────────────────┐
  │  КОД ДЛЯ ВХОДА                         │
  │                                        │
  │      515325                            │
  │                                        │
  │  для edamkaldybek@gmail.com
  └────────────────────────────────────────┘
```

Так разрабатывают всегда: подключать почтовый сервис ради каждой проверки
долго, а в случае SMS ещё и платно. Заглушка ведёт себя точно так же с
точки зрения остального кода.

При запуске сервер честно предупреждает, в каком он режиме:

```
письма НЕ отправляются — код входа будет напечатан здесь
```

### Как подключить настоящую почту

Ничего в коде менять не надо — только задать переменные окружения.
Для Gmail:

1. Включи двухфакторную защиту в аккаунте Google
2. Создай **пароль приложения** (Аккаунт → Безопасность → Пароли
   приложений). Обычный пароль от почты не подойдёт
3. Запусти сервер так:

```powershell
$env:SMTP_HOST="smtp.gmail.com"
$env:SMTP_PORT="587"
$env:SMTP_USER="твоя.почта@gmail.com"
$env:SMTP_PASSWORD="пароль-приложения"
dart run bin\server.dart
```

Теперь при запуске будет написано `письма отправляются через SMTP`.

На хостинге эти же переменные задаются в настройках сервиса. **В коде их
писать нельзя**: репозиторий попадёт на GitHub вместе с паролем.

Про доставляемость: письма с бесплатного хостинга часто попадают в спам —
почтовые службы не доверяют незнакомым отправителям. Для учёбы это
терпимо, для настоящего приложения берут специальный сервис рассылок.

### Что защищает вход

Сам по себе шестизначный код — слабая защита: вариантов миллион, и
перебрать их машина может за минуты. Работает он только вместе с
ограничениями:

| Ограничение | Зачем |
|---|---|
| код живёт 5 минут | подобранный однажды код не работает вечно |
| 3 попытки ввода | миллион вариантов не перебрать по три за раз |
| 5 кодов на почту в час | нельзя завалить чужой ящик письмами |
| код одноразовый | подошёл — и больше не действует |
| в базе хранится отпечаток | украдут базу — кодов оттуда не достать |

Последнее стоит пояснить. В таблице лежит не сам код, а результат
необратимого преобразования — **отпечаток**. Проверка работает не
«сравни коды», а «посчитай отпечаток присланного и сравни отпечатки».
Так же хранят пароли в любом приличном приложении.

Ограничение на частоту, кстати, сначала не работало: я удалял прежние
коды, а счётчик считает именно их. Нашлось простой проверкой — шесть
запросов подряд прошли все шесть. Теперь прежние коды не удаляются, а
гасятся: подойти не могут, но в истории остаются.

### Почему почта, а не SMS

Письма бесплатны. Каждое SMS стоит денег, в том числе каждая проверка при
отладке, а для собственного имени отправителя иногда нужно ещё и юрлицо.

Код при этом написан так, что переход на SMS — это **один новый класс**:

```dart
abstract class CodeSender {
  Future<void> send(String address, String code);
}
```

Есть `ConsoleCodeSender` (печатает) и `SmtpCodeSender` (шлёт письмо).
Добавить `SmsCodeSender` — и поменять одну строку в `bin/server.dart`.

Третий раз в проекте один и тот же приём: описываем **умение**, а не
исполнителя. Сначала так поступили с хранилищем смен, потом с тем,
«кто сейчас действует», теперь с доставкой кода.

### Чего в этой авторизации всё ещё нет

- **токен не протухает** — выдан навсегда, отозвать можно только выходом
- **нет ограничения на частоту** остальных запросов, только на коды
- **письма могут попасть в спам** — см. выше

Зато закрыто главное: раньше достаточно было назвать чужой номер телефона.
Теперь нужен доступ к почте.

## 7. PostgreSQL вместо файла

### Зачем

Файл SQLite лежит на диске сервиса. На бесплатном хостинге этот диск
**временный**: сервис перезапустился — файла нет, вместе с ним нет
аккаунтов, смен и записей. А перезапускается он сам по себе, без спроса.

PostgreSQL — отдельная служба со своим хранилищем. Перезапуск сервера её
не касается.

### Как включить

Никак не переписывая код. Сервер смотрит на переменную окружения:

```
есть DATABASE_URL  →  PostgreSQL
нет DATABASE_URL   →  файл SQLite
```

Локально, если захочешь попробовать:

```powershell
$env:DATABASE_URL="postgres://пользователь:пароль@адрес:5432/имя_базы"
dart run bin\server.dart
```

При запуске сервер честно говорит, что выбрал:

```
база: PostgreSQL
```

На Render база описана прямо в `render.yaml` — он создаст её сам и
подставит адрес. Ничего вбивать руками не нужно.

### Что пришлось поправить — и чему это учит

Переезд — не «поменять одну строчку». Таблицы и запросы остались те же,
но **база не одна и та же программа**, и мелкие различия вылезли сразу.
Каждое ломало сервер при запуске или на первом же запросе.

**1. Логический тип.** В SQLite нет отдельного «да/нет»: такие колонки
хранят числами 0 и 1 с проверкой `CHECK (x IN (0, 1))`. PostgreSQL такую
проверку не принимает — у него есть настоящий `boolean`, и сравнивать его
с числом он отказывается.

Решилось не правкой кода, а настройкой генератора: в `build.yaml` теперь
перечислены оба диалекта, и drift делает схему, подходящую обоим.

**2. PRAGMA.** Строка `PRAGMA foreign_keys = ON` включает в SQLite
проверку внешних ключей — редкая особенность, почти любая другая база
следит за ними всегда. PostgreSQL слова `PRAGMA` не знает вовсе.

Теперь она выполняется только для SQLite.

**3. Подстановки в запросах.** Мы пишем так:

```sql
WHERE email = ? AND created_at > ?
```

PostgreSQL их нумерует:

```sql
WHERE email = $1 AND created_at > $2
```

Чтобы не держать два набора запросов, перевод делается в одном месте —
`AppDatabase.query`. Все свои запросы идут через него, а не через
`customSelect` напрямую: иначе однажды кто-нибудь напишет мимо, и
сломается это только на сервере.

**4. Среднее значение.** `AVG` в SQLite возвращает обычное число, а в
PostgreSQL — «точный» тип, который драйвер отдаёт **строкой**, чтобы не
потерять разряды. Чтение как числа падало.

Лечится приведением прямо в запросе:
`CAST(AVG(rating) AS DOUBLE PRECISION)`. Оно понятно обеим базам.

### Вывод

SQL называют общим языком, и это правда — но у каждой базы свой выговор.
Запросы переносятся почти без правок, а вот всё вокруг них — типы,
служебные команды, форма подстановок — различается.

Отсюда и практическое правило: **если знаешь, что переедешь, проверь
переезд заранее**. Все четыре различия нашлись за полчаса, потому что
было где запустить настоящий PostgreSQL. Обнаружить их впервые на
работающем сервисе с живыми пользователями — совсем другое дело.

## 8. Запуск на телефоне

### Android

Нужен **Android Studio** — из него ставится всё остальное (SDK, драйверы,
инструменты). Скачай с
[developer.android.com/studio](https://developer.android.com/studio),
поставь, запусти один раз и дай ему доустановить компоненты.

Потом в PowerShell:

```powershell
flutter doctor
```

Он покажет, чего не хватает. Если ругается на лицензии:

```powershell
flutter doctor --android-licenses
```

и нажимай `y` на всё.

**На телефоне** включи режим разработчика: Настройки → О телефоне →
семь раз нажать на «Номер сборки». Потом Настройки → Для разработчиков →
включить «Отладка по USB».

Подключи телефон кабелем, разреши отладку во всплывающем окне и проверь:

```powershell
flutter devices
```

Телефон должен появиться в списке. Запуск:

```powershell
flutter run -d <имя_устройства> --dart-define=API_URL=https://адрес-сервера
```

Или собрать файл, который можно установить:

```powershell
flutter build apk --release --dart-define=API_URL=https://адрес-сервера
```

Готовый файл окажется в
`build\app\outputs\flutter-apk\app-release.apk` — его можно перекинуть
на телефон и установить.

### Какой адрес писать

Вот тут кроется главная ловушка.

`localhost` на телефоне означает **сам телефон**, а не твой компьютер.
Указать `http://localhost:8080` — значит попросить телефон найти сервер
внутри себя. Он не найдёт.

Два выхода:

**1. Адрес сервера в интернете** (раздел 3). Это правильный путь и ровно
та причина, по которой сервер стоит выложить.

**2. Адрес компьютера в домашней сети** — если телефон и компьютер в
одной Wi-Fi. Узнать адрес:

```powershell
ipconfig
```

Ищи строку `IPv4-адрес` вида `192.168.1.5`. Тогда:

```powershell
flutter run -d <устройство> --dart-define=API_URL=http://192.168.1.5:8080
```

Может понадобиться разрешить порт в брандмауэре Windows — он спросит сам
при первом запуске сервера, ответь «Разрешить доступ» для частных сетей.

### iPhone

Собрать приложение для iPhone **с Windows нельзя**. Apple требует Mac —
это её правило, а не ограничение Flutter. Варианты: чужой Mac, аренда
Mac в облаке, либо пока остаться на Android.

Код при этом уже готов: тот же самый проект собирается под iPhone без
единой правки, когда появится Mac.
