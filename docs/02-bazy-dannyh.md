# Базы данных — справочник

## 1. Зачем вообще нужна БД

Пока приложение запущено, данные живут в **оперативной памяти** (переменные,
списки). Закрыл приложение — память освободилась, данные исчезли.

Чтобы данные пережили перезапуск, их надо записать в **файл на диске**.
Но простой файл — плохое хранилище:

| Проблема простого файла | Что делает БД |
|---|---|
| Чтобы найти одну запись, надо прочитать весь файл | Индексы: находит запись, не читая остальное |
| Два одновременных изменения портят файл | Блокировки и транзакции |
| Нет проверки структуры — можно записать мусор | Схема и ограничения (constraints) |
| Оборвалась запись на середине → файл битый | Журнал: либо операция целиком, либо никак |

**БД — это программа, которая управляет файлами вместо тебя и даёт гарантии.**

---

## 2. Виды баз данных

| Вид | Примеры | Модель данных | Когда брать |
|---|---|---|---|
| Реляционные (SQL) | SQLite, PostgreSQL, MySQL | Таблицы + связи, строгая схема | Данные связаны между собой |
| Ключ-значение | Redis, Hive, SharedPreferences | `ключ → значение` | Настройки, кэш, токены |
| Документные | MongoDB, Firestore | JSON-документы, гибкая схема | Слабо связанные данные |
| Графовые | Neo4j | Узлы и рёбра | Соцсети, маршруты |

Для fastwork берём **реляционную**: пользователь → заказы → отклики → отзывы —
это плотная сеть связей, а именно с ними реляционная модель работает лучше всех.

---

## 3. Где физически лежит база

| | Локальная (SQLite) | Серверная (PostgreSQL) |
|---|---|---|
| Где файл | На телефоне пользователя | На сервере в дата-центре |
| Кто видит данные | Только владелец телефона | Все пользователи |
| Нужен интернет | Нет | Да |
| Кто может подменить | Владелец устройства | Только владелец сервера |

> **Важно для fastwork.** Работник должен видеть заказ, который создал
> работодатель — то есть данные одного пользователя должны попасть другому.
> Локальная БД этого не умеет физически. Значит боевой fastwork **обязан**
> иметь сервер, а SQLite у нас — учебный полигон и будущий кэш.

## 4. Базовые термины

### Таблица, строка, колонка
Таблица — список однотипных записей. Колонка — одно поле с типом. Строка — один объект.

### Схема (schema)
Описание структуры: какие таблицы, колонки, типы, ограничения. В SQL схема
**строгая**: БД не даст записать текст в числовую колонку.

### Первичный ключ (PRIMARY KEY)
Колонка, однозначно определяющая строку. Обычно `id INTEGER`.

Почему не имя или телефон? Ключ обязан быть уникальным **и неизменным**.
Имена повторяются, телефон можно сменить — а на ключ уже ссылаются другие
таблицы, и менять его означает чинить ссылки по всей базе.

### Внешний ключ (FOREIGN KEY)
Колонка, ссылающаяся на `id` в другой таблице. Так строятся связи.

```sql
CREATE TABLE jobs (
  id           INTEGER PRIMARY KEY,
  employer_id  INTEGER NOT NULL REFERENCES users(id),
  title        TEXT    NOT NULL
);
```

Даёт **ссылочную целостность**: нельзя создать заказ с `employer_id = 999`,
если такого пользователя нет. БД откажет.

При удалении пользователя нужно решить, что делать с его заказами:
- `ON DELETE RESTRICT` — запретить удаление, пока есть заказы (безопасно)
- `ON DELETE CASCADE` — удалить заказы следом (опасно, легко потерять данные)
- `ON DELETE SET NULL` — обнулить ссылку

### Типы связей

**1:1** — один к одному. `users` ↔ `wallets`: ровно один кошелёк на человека.
FK + UNIQUE.

**1:М** — один ко многим. Самая частая. У работодателя много заказов.
FK лежит **на стороне «многих»** — в `jobs`, а не в `users`.

**М:М** — многие ко многим. Работник ↔ заказы. Напрямую не выражается,
нужна третья таблица-связка (`applications`) с двумя внешними ключами.

### Ограничения (constraints)
| Ограничение | Смысл |
|---|---|
| `NOT NULL` | Значение обязательно |
| `UNIQUE` | Значения не повторяются |
| `CHECK (rating BETWEEN 1 AND 5)` | Проверка значения |
| `DEFAULT 0` | Значение по умолчанию |

Ограничение в БД **надёжнее проверки в коде**: код можно обойти (баг,
другая версия приложения, прямой запрос), а БД откажет всегда.

### Индекс
Индекс — отдельная структура «значение → где лежит строка».

Аналогия: чтобы найти человека в телефонной книге на 1000 страниц, ты не
читаешь её подряд — книга отсортирована по фамилии. Индекс делает то же.

Без индекса поиск заказов на дату читает **всю таблицу** (full scan).
С индексом по `work_date` — сразу нужный участок.

```sql
CREATE INDEX idx_jobs_work_date ON jobs(work_date);
```

Цена индекса: занимает место и **замедляет запись** (при каждой вставке
надо обновить и индекс). Поэтому индексы ставят на колонки, по которым
реально ищут и сортируют, а не на все подряд.

### Нормализация
Правило: **один факт хранится в одном месте.**

Плохо — название категории текстом в каждом заказе:
```
jobs: id | title        | category
      1  | Грузчик      | Логистика
      2  | Курьер       | Логистика
      3  | Разнорабочий | Логистка     <- опечатка, и это уже другая категория
```
Переименовать категорию = обновить тысячи строк, а опечатки создают
категории-призраки.

Хорошо — категория живёт в своей таблице, заказ хранит `category_id`.
Переименование = одна строка. Опечатка невозможна: FK не даст сослаться
на несуществующую категорию.

### Транзакция и ACID
Транзакция — группа операций, которая выполняется **целиком или никак**.

Перевод денег работнику:
```sql
BEGIN;
  UPDATE wallets SET balance_held = balance_held - 12500 WHERE user_id = 1;
  UPDATE wallets SET balance_available = balance_available + 12500 WHERE user_id = 2;
COMMIT;
```
Если между строками сядет батарейка, без транзакции деньги **исчезнут**:
у одного списались, другому не пришли. Транзакция гарантирует, что при
сбое откатится всё (`ROLLBACK`).

**ACID** — четыре гарантии:
- **A**tomicity — целиком или никак
- **C**onsistency — ограничения не нарушаются
- **I**solation — параллельные транзакции не видят промежуточных состояний друг друга
- **D**urability — после `COMMIT` данные переживут отключение питания

Для кошелька fastwork транзакции — не роскошь, а обязательное условие.

### Миграция
Схема меняется со временем: добавил колонку, новую таблицу. У пользователей
на телефонах уже стоит старая версия с их данными.

Миграция — скрипт «как перевести схему версии N в версию N+1 **без потери
данных**». БД хранит номер версии и применяет недостающие миграции при запуске.

### ORM
Писать SQL строками неудобно: опечатка находится только в рантайме, а
результат приходит как `Map<String, dynamic>` без типов.

ORM (в Flutter — **Drift**) описывает таблицы кодом на Dart и генерирует
типобезопасные классы. Ошибку в имени колонки ловит компилятор, а на выходе
получаешь объект `Job`, а не безымянную мапу.

## 5. SQL — минимум

```sql
-- выбрать опубликованные заказы на дату
SELECT * FROM jobs
WHERE work_date = 1758758400 AND status = 'published'
ORDER BY payment_amount DESC;

-- заказы вместе с именем работодателя (JOIN соединяет таблицы по ключу)
SELECT jobs.title, jobs.payment_amount, users.full_name
FROM jobs
JOIN users ON users.id = jobs.employer_id;

-- сколько откликов на каждом заказе (GROUP BY — группировка + агрегат)
SELECT job_id, COUNT(*) AS cnt
FROM applications
GROUP BY job_id;

-- средний рейтинг пользователя
SELECT AVG(rating) FROM reviews WHERE target_id = 7;

INSERT INTO categories (name) VALUES ('Логистика');
UPDATE jobs SET status = 'done' WHERE id = 3;
DELETE FROM applications WHERE id = 10;
```

`JOIN` — главная операция реляционной БД: она собирает данные, разложенные
по разным таблицам, обратно в одну выборку. Именно ради `JOIN` данные и
разделяют на таблицы.

## 6. Как БД выполняет запрос

1. **Парсер** — разбирает текст запроса, проверяет синтаксис.
2. **Планировщик** — решает, *как* искать: по индексу или полным перебором.
   Один и тот же запрос может выполняться миллисекунду или минуту — разница
   в плане.
3. **Исполнитель** — читает страницы данных с диска, применяет фильтры, соединяет.
4. **Результат** — строки отдаются приложению.

Посмотреть план можно так: `EXPLAIN QUERY PLAN SELECT ...` — покажет,
использовался индекс (`USING INDEX`) или был полный скан (`SCAN TABLE`).
