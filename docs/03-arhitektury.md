# Архитектуры приложений — справочник

## 1. Что такое архитектура

Архитектура — **не структура папок**. Это набор решений о том, где лежит
ответственность и **куда направлены зависимости** между частями кода.

Цель у неё ровно одна: **сделать изменения дешёвыми**. Код пишут один раз,
а меняют сотни раз. Архитектура проигрывает или выигрывает на изменениях.

### Что бывает без архитектуры

Весь код в одном виджете: запрос к БД, подсчёт комиссии, верстка — вперемешку.

```dart
class JobsPage extends StatefulWidget {
  // ... 800 строк: sqlite + http + расчёт цены + верстка
}
```

Пока экранов три — работает. Дальше начинается:
- **Нельзя протестировать** бизнес-правило, не запустив весь интерфейс с БД.
- **Нельзя переиспользовать**: та же логика нужна на втором экране — копипаста.
- **Меняешь БД — переписываешь экраны.** Логика прибита к источнику данных.
- **Правка в одном месте ломает другое**: всё связано со всем.

---

## 2. Единственная идея под всеми архитектурами

В любом приложении есть ровно три вида ответственности:

1. **Показать и принять ввод** — интерфейс
2. **Решить, что можно, а что нельзя** — бизнес-правила
3. **Взять и сохранить данные** — БД, сеть, файлы

Все архитектуры — это разные ответы на два вопроса:
**как их разделить** и **кто от кого зависит**.

## 3. Семейства архитектур

### Важное разделение

Термины часто валят в одну кучу, хотя они про разное:

| Группа | Про что | Примеры |
|---|---|---|
| Организация **всего** приложения | Как делится проект целиком | Layered, Clean, Hexagonal, Onion |
| Организация **слоя интерфейса** | Как экран связан с логикой | MVC, MVP, MVVM, MVI |

**Они не конкурируют, а вкладываются друг в друга.** BLoC живёт *внутри*
слоя presentation Clean Architecture. «Clean или MVVM?» — вопрос
некорректный, как «машина или двигатель?».

---

### MVC — Model-View-Controller (1979, Smalltalk)
- **Model** — данные и правила
- **View** — отображение
- **Controller** — принимает ввод, меняет модель

Проблема: границы размыты, Controller разрастается. Сейчас в чистом виде
почти не встречается на клиенте, живёт в вебе (Rails, Laravel, Spring MVC).

### MVP — Model-View-Presenter
View становится **пассивной**: она объявляет интерфейс (`showJobs()`,
`showError()`), а Presenter им управляет. Вся логика в Presenter, и его
можно тестировать, подставив фиктивную View.

Плюс: тестируемость. Минус: много ручной связки, на каждый экран — интерфейс.
Эпоха Android до 2018.

### MVVM — Model-View-ViewModel
ViewModel выставляет **наблюдаемое состояние**, View на него подписана и
перерисовывается сама. ViewModel про View ничего не знает.

Сегодня это мейнстрим: Android (Jetpack), iOS (SwiftUI), Flutter (Provider,
Riverpod, ChangeNotifier).

### MVI / однонаправленный поток (сюда же BLoC)
Поток данных строго по кругу и только в одну сторону:

```
Событие (нажал кнопку) → обработчик → новое состояние → перерисовка UI
      ▲                                                        │
      └────────────────────────────────────────────────────────┘
```

Состояние **неизменяемо**: не правится, а заменяется новым целиком.

Плюс: в любой момент видно, какое состояние и почему; поведение
воспроизводимо, легко тестировать и логировать. Минус: многословно.

Это и есть **BLoC**, который мы выбрали.

### Layered / N-tier — слоёная
Presentation → Business → Data. Зависимости идут **строго вниз**.

Минус: бизнес-слой зависит от слоя данных. Меняется БД — трясёт логику.
Именно это и чинит Clean Architecture.

### Clean Architecture (Роберт Мартин, 2012)
Слои + **инверсия зависимостей**: логика в центре и не зависит ни от чего.

### Hexagonal / Ports & Adapters (Кокбёрн, 2005) и Onion (2008)
По сути **та же идея**, другая метафора: ядро приложения, «порты»
(интерфейсы) и «адаптеры» (реализации для БД, сети, UI). Если понял Clean —
понял и эти.

## 4. Clean Architecture подробно

### Слои

```
┌──────────────────────────────────────────────┐
│  Frameworks: Flutter, SQLite, HTTP           │  ← меняется часто
│  ┌────────────────────────────────────────┐  │
│  │  Adapters: BLoC, Repository Impl, DTO  │  │
│  │  ┌──────────────────────────────────┐  │  │
│  │  │  Use Cases: сценарии             │  │  │
│  │  │  ┌────────────────────────────┐  │  │  │
│  │  │  │  Entities: суть предметной │  │  │  │
│  │  │  │  области                   │  │  │  │  ← меняется редко
│  │  │  └────────────────────────────┘  │  │  │
│  │  └──────────────────────────────────┘  │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

### Главное правило — The Dependency Rule

> **Зависимости в коде направлены только внутрь.**
> Внутренний слой ничего не знает о внешнем.

Проверка: в файле из `domain/` **не должно быть ни одного импорта**
Flutter, sqlite, http. Только чистый Dart. Если импорт появился — правило
нарушено.

**Зачем?** Внутри — стабильное (что такое заказ и по каким правилам он
оплачивается), снаружи — переменчивое (Flutter, выбранная БД, чужой API).
Нельзя, чтобы стабильное ломалось при смене переменчивого.

### Инверсия зависимостей — механизм, который это делает возможным

Логике *нужны* данные из БД. Как не зависеть от неё?

**Интерфейс объявляется во внутреннем слое, а реализуется во внешнем.**

```dart
// domain/repositories/job_repository.dart — ЧТО нужно. Чистый Dart.
abstract class JobRepository {
  Future<List<Job>> getJobsByDate(DateTime date);
}

// data/repositories/job_repository_impl.dart — КАК это делается.
class JobRepositoryImpl implements JobRepository {
  final JobLocalDataSource local;
  JobRepositoryImpl(this.local);

  @override
  Future<List<Job>> getJobsByDate(DateTime date) async {
    final models = await local.getJobsByDate(date);
    return models.map((m) => m.toEntity()).toList();
  }
}
```

Стрелка зависимости **развернулась**: не domain зависит от data, а data
зависит от domain — потому что реализует его интерфейс.

Практический результат: на этапе 7 мы заменим SQLite на сервер. Появится
новый `JobRepositoryImpl`, а `domain/` и экраны **не изменятся ни на строчку**.
Ради этого всё и затевалось.

### Сущность (Entity) и модель (Model) — зачем два похожих класса

```dart
// domain/entities/job.dart — чистая суть. Ничего не знает о JSON и БД.
class Job {
  final int id;
  final String title;
  final int paymentAmount;
  const Job({required this.id, required this.title, required this.paymentAmount});
}

// data/models/job_model.dart — знает, как лежит снаружи.
class JobModel {
  final int id;
  final String title;
  final int paymentAmount;

  factory JobModel.fromJson(Map<String, dynamic> json) => JobModel(
    id: json['id'],
    title: json['job_title'],        // у сервера имя другое
    paymentAmount: json['pay_amount'],
  );

  Job toEntity() => Job(id: id, title: title, paymentAmount: paymentAmount);
}
```

Сервер переименовал `job_title` → `name`? Меняется **один** `fromJson`.
Экраны, BLoC и use case не трогаются. Без разделения пришлось бы искать
`job_title` по всему проекту.

### Use Case — один сценарий, один класс

```dart
class GetJobsByDate {
  final JobRepository repository;
  GetJobsByDate(this.repository);

  Future<List<Job>> call(DateTime date) => repository.getJobsByDate(date);
}
```

Читая список файлов в `usecases/`, ты видишь **что приложение умеет**:
`GetJobsByDate`, `ApplyToJob`, `HoldPayment`, `ReleasePayment`.

### Структура папок

```
lib/
  core/                      общее для всех фич: ошибки, константы, DI
  features/
    jobs/
      domain/
        entities/job.dart
        repositories/job_repository.dart      абстракция
        usecases/get_jobs_by_date.dart
      data/
        models/job_model.dart
        datasources/job_local_datasource.dart
        repositories/job_repository_impl.dart  реализация
      presentation/
        bloc/
        pages/
        widgets/
```

Деление **по фичам, а не по типам файлов**: всё про заказы лежит рядом.
При `lib/blocs/`, `lib/models/`, `lib/pages/` одна фича размазана по всему
проекту, и правка требует прыжков между папками.

### Путь данных: открыли ленту на дату

```
JobsPage (виджет)
   │  отправляет событие LoadJobs(date)
   ▼
JobsBloc                       presentation
   │  вызывает
   ▼
GetJobsByDate (use case)       domain
   │  зовёт через интерфейс
   ▼
JobRepository (abstract)       domain
   │  подставлена реализация
   ▼
JobRepositoryImpl              data
   │
   ▼
JobLocalDataSource → SQLite    data
   │
   ▼  наверх: JobModel → Job → JobsLoaded(jobs) → перерисовка экрана
```

## 5. Цена Clean Architecture

Честно: она **многословна**. Одна фича — это entity, модель, источник
данных, интерфейс репозитория, реализация, use case, BLoC, события,
состояния, экран. Для приложения из трёх экранов это избыточно.

| Оправдана | Избыточна |
|---|---|
| Проект живёт годами | Прототип, MVP на выброс |
| Команда из нескольких человек | Один разработчик, два экрана |
| Источник данных будет меняться | Источник зафиксирован навсегда |
| Нужны тесты бизнес-логики | Логики почти нет, только вёрстка |

Для fastwork оправдана: проект учебный и долгий, а источник данных
**точно** поменяется (локальная БД → сервер).
