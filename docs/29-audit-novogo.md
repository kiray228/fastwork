# Проверка нового кода: что нашлось и что исправлено

После раундов с гостевой лентой, «знакомыми», санкнижкой и
приглашениями новый код прочитали отдельно — в поисках дыр, а не
функций. Главная находка обесценивала санкнижку целиком.

## 1. Документ «проверял» сам владелец

Адрес `POST /api/documents/<id>/review` был открыт любому вошедшему, а
приложение само «одобряло» загруженный документ через две секунды.
Значит, любой мог загрузить санкнижку с выдуманным номером и без срока —
и записаться на смену с продуктами. Тот же путь ставил отметку
«проверен» по удостоверению.

Теперь:

- С сервером документы проверяет **оператор** служебным ключом
  (`X-Admin-Key`, как для МРП). Старого адреса нет.
- Приложение одобряет документ само только без сервера, где оператора
  нет: `DocumentRepository.selfReview`. С сервером документ остаётся
  «на проверке», пока оператор не решит.
- Принимаются только известные типы (`kDocumentTypes`), санкнижка — только
  со сроком действия.

Как проверять документы оператору:

```
curl -H "X-Admin-Key: $ADMIN_KEY" https://fastwork-server.onrender.com/api/admin/documents
curl -X POST -H "X-Admin-Key: $ADMIN_KEY" -H "Content-Type: application/json" \
  -d '{"approved": true}' https://fastwork-server.onrender.com/api/admin/documents/12/review
```

Первый показывает очередь: кто, какой документ, номер, срок. Второй —
решение (`false` — отклонить).

## 2. Гость мог выкачать всю историю смен

Номера смен идут подряд, а `/api/public/shifts/<id>` отдавал любую
оплаченную смену — отменённые, прошедшие, другие города, с номером
аккаунта заказчика. Теперь гостю — только смены, которые ещё не
кончились и не отменены, и без `createdBy`.

## 3. Лента без входа нагружала базу

Каждый запрос ленты гостя — полтора десятка запросов к базе, без
предела частоты. Теперь `/api/public/*` ограничены — 200 запросов в
минуту с адреса, — а лента каждого города кэшируется на 30 секунд:
гости смотрят одно и то же.

## 4. Санкнижка и перенос смены

Заказчик мог передвинуть смену с продуктами дальше срока санкнижки
записавшегося — и тот оставался записанным. Теперь при переносе это
проверяется так же, как пересечение с другими сменами: запись
снимается без штрафа, человеку и заказчику приходит объяснение
(«к новой дате ваша санитарная книжка уже не действует»).

## 5. Санкнижка и ночная смена

Срок сверялся с днём начала смены. Ночная смена 22:00–06:00 с книжкой,
истекающей в день начала, проходила, хотя к утру книжка уже не
действует. Теперь срок сверяется с днём конца смены.

## 6. Удалённые аккаунты

- Удалённый аккаунт оставался в «знакомых» заказчика, и ему можно было
  отправить приглашение. Теперь его там нет, а приглашение отклоняется.
- Удалённый мог засчитаться пригласившим, а приглашённые с удалённых
  аккаунтов — в счётчике. Исправлено.
- Номер пригласившего не стирался с телефона после регистрации, и
  следующую регистрацию с того же телефона засчитали бы тому же
  человеку. Теперь он стирается.

## Что проверено и в порядке

Даты в SQLite и Postgres хранятся одинаково (числом секунд), запросы
`knownWorkers` и `referralStats` работают в обеих базах, других путей
записи в обход проверки санкнижки нет (лист ожидания и приглашения
только уведомляют).

## Тесты

- Сервер: одобряет только оператор, очередь документов, неизвестный тип
  и санкнижка без срока отклоняются, отменённая смена гостю — 404, без
  `createdBy`, предел частоты на `/api/public/*`.
- База: ночная смена и срок книжки, перенос смены за срок книжки
  снимает запись, удалённый аккаунт не в «знакомых», позвать его нельзя,
  приглашение по его ссылке не засчитывается.
