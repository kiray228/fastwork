# fastwork — модель данных (этап 1)

Документ описывает, **какие сущности живут в приложении и как они связаны**.
Схема БД — фундамент: слои Clean Architecture строятся поверх неё.

---

## 1. Словарь терминов

| Термин | Что это |
|---|---|
| Таблица | Список однотипных записей. Одна таблица = одна сущность. |
| Строка (запись) | Один конкретный объект: один заказ, один пользователь. |
| Первичный ключ (PK) | Колонка `id`, уникально идентифицирующая строку. |
| Внешний ключ (FK) | Колонка, ссылающаяся на `id` строки в другой таблице. Так строятся связи. |
| Связь 1-ко-многим | У одного работодателя много заказов. FK лежит на «стороне многих» (в `jobs`). |
| Связь многие-ко-многим | Много работников ↔ много заказов. Реализуется третьей таблицей (`applications`). |
| Ограничение UNIQUE | Запрет дубликатов. БД физически не даст записать вторую такую строку. |

## 2. Таблицы

### users — пользователи
| Колонка | Тип | Заметки |
|---|---|---|
| id | INTEGER PK | |
| phone | TEXT UNIQUE | логин |
| password_hash | TEXT | **никогда** не храним пароль в открытом виде |
| full_name | TEXT | |
| avatar_path | TEXT NULL | |
| role | TEXT | `worker` / `employer` / `admin` |
| rating | REAL NULL | кэш среднего рейтинга из reviews |
| created_at | INTEGER | Unix-время |

> **Почему одна таблица, а не две (работник и работодатель)?**
> У них 90% одинаковых полей: имя, телефон, пароль, аватар, рейтинг.
> Две таблицы означали бы дублирование логики авторизации, а отзывы и кошелёк
> не смогли бы единообразно ссылаться на «пользователя».
> Роль — это **свойство** пользователя, а не отдельный вид сущности.

### categories — категории подработок
| Колонка | Тип |
|---|---|
| id | INTEGER PK |
| name | TEXT UNIQUE |
| icon_code | INTEGER |

### jobs — заказы (подработки)
| Колонка | Тип | Заметки |
|---|---|---|
| id | INTEGER PK | |
| employer_id | INTEGER FK → users.id | кто создал |
| category_id | INTEGER FK → categories.id | |
| title | TEXT | |
| description | TEXT | |
| work_date | INTEGER | **дата смены** — по ней идёт поиск на главном экране |
| start_minutes | INTEGER | начало, минут от полуночи |
| end_minutes | INTEGER | конец |
| address | TEXT | |
| payment_amount | INTEGER | **в тиынах/копейках, целое число** |
| status | TEXT | `draft` / `published` / `in_progress` / `done` / `cancelled` |
| created_at | INTEGER | |

> **Почему деньги — целое число, а не дробное?**
> Дробные числа в компьютере хранятся приблизительно: `0.1 + 0.2` даёт
> `0.30000000000000004`. На деньгах такая ошибка — это потерянные копейки и
> несходящийся баланс. Поэтому храним **минимальную единицу целым числом**
> (12 500 тиын), а делим на 100 только при показе на экране.

### applications — отклики
| Колонка | Тип | Заметки |
|---|---|---|
| id | INTEGER PK | |
| job_id | INTEGER FK → jobs.id | |
| worker_id | INTEGER FK → users.id | |
| status | TEXT | `pending`/`accepted`/`rejected`/`withdrawn`/`completed` |
| cover_message | TEXT NULL | |
| created_at | INTEGER | |
| UNIQUE(job_id, worker_id) | | нельзя откликнуться дважды |

> Это **таблица-связка** для отношения многие-ко-многим: один работник
> откликается на много заказов, на один заказ откликается много работников.
>
> **Где «архивные отклики»?** Отдельной таблицы нет и не нужно.
> Архив — это не другая сущность, а **другое состояние той же сущности**:
> отклики со статусом `completed`, `rejected` или `withdrawn`.
> Копировать строки в «архивную таблицу» — классическая ошибка новичка:
> данные разъезжаются, а любой отчёт приходится писать дважды.

### wallets — кошельки
| Колонка | Тип | Заметки |
|---|---|---|
| id | INTEGER PK | |
| user_id | INTEGER FK → users.id UNIQUE | один кошелёк на пользователя |
| balance_available | INTEGER | свободные деньги |
| balance_held | INTEGER | заморожено под сделки (эскроу) |

### transactions — журнал операций
| Колонка | Тип | Заметки |
|---|---|---|
| id | INTEGER PK | |
| wallet_id | INTEGER FK → wallets.id | |
| job_id | INTEGER FK → jobs.id NULL | по какой сделке |
| type | TEXT | `deposit`/`withdraw`/`hold`/`release`/`refund`/`fee` |
| amount | INTEGER | со знаком: + приход, − расход |
| balance_after | INTEGER | баланс после операции |
| created_at | INTEGER | |

> **Зачем журнал, если баланс уже есть в wallets?**
> Число баланса отвечает «сколько сейчас», но не отвечает «почему столько».
> Когда пользователь скажет «у меня пропали деньги», без журнала это
> недоказуемо. Так устроен любой банк: баланс — это итог, а истина — в
> списке операций. Баланс всегда обязан сходиться с суммой транзакций.

### reviews — отзывы
| Колонка | Тип | Заметки |
|---|---|---|
| id | INTEGER PK | |
| job_id | INTEGER FK → jobs.id | по какой сделке |
| author_id | INTEGER FK → users.id | кто пишет |
| target_id | INTEGER FK → users.id | о ком пишут |
| rating | INTEGER | 1..5 |
| comment | TEXT NULL | |
| created_at | INTEGER | |
| UNIQUE(job_id, author_id) | | один отзыв на сделку от одного автора |

> Отзыв ссылается на users **дважды** — автор и адресат. Так одна таблица
> обслуживает отзывы в обе стороны.
> Привязка к `job_id` обязательна: она доказывает, что сделка реально была,
> и защищает от накрутки рейтинга выдуманными отзывами.

### support_tickets / support_messages — техподдержка
`support_tickets`: id PK, user_id FK, subject, status (`open`/`in_progress`/`closed`), created_at
`support_messages`: id PK, ticket_id FK → support_tickets.id, sender_id FK → users.id, text, created_at

> Переписка — тоже связь 1-ко-многим: одно обращение → много сообщений.

## 3. Карта связей

```
categories ──1:М──► jobs ◄──М:1── users (employer)
                     │
                     ├──1:М──► applications ──М:1──► users (worker)
                     ├──1:М──► reviews ──► users (author) + users (target)
                     └──1:М──► transactions ──М:1──► wallets ──1:1──► users

users ──1:М──► support_tickets ──1:М──► support_messages
```

## 4. Сценарий эскроу (гарант оплаты)

1. Работодатель публикует заказ → `hold`: `available −= сумма`, `held += сумма`.
   Деньги у него уже нельзя потратить, но работнику ещё не ушли.
2. Работник откликается → `applications` со статусом `pending`.
3. Работодатель принимает → `accepted`, заказ переходит в `in_progress`.
4. Работа выполнена, обе стороны подтверждают → `release`:
   у работодателя `held −= сумма`; работнику `available += сумма − комиссия`;
   платформе `fee`. Каждый шаг пишется в `transactions`.
5. Спор → тикет в поддержку → `refund` (возврат) или `release` (выплата).

> **Честное предупреждение.** Настоящий эскроу нельзя реализовать внутри
> мобильного приложения: код на телефоне пользователя нельзя считать
> доверенным, его можно вскрыть и подменить. Реальные деньги требуют
> серверной части, платёжного провайдера, а «легальность» — юрлица, оферты
> и налогового статуса сторон. Это вне задач учебного проекта.
> Поэтому на этапе 1 мы строим **симуляцию кошелька локально**. Логика
> состояний и проводок при этом ровно та же, что в бою, — а на этапе 2 мы
> перенесём её на сервер, и ты увидишь, почему её место именно там.
